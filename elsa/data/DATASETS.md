# OT3/FineWeb dataset naming

Three distinct OpenThoughts3+FineWeb-Edu builds exist in this directory and get
confused easily. Use these short names when discussing them; symlinks with the
same names point at the real files below.

| Short name | Real file | Tokenizer | Notes |
|---|---|---|---|
| **LEGACY-20K** | `ot3_fineweb_20k.jsonl` | DeepSeek-R1-Distill-Qwen-1.5B | Built pre-08-04. Build script never got committed to git and is lost — reverse-engineered by diffing against raw OpenThoughts3-1.2M. ~62% of rows keep the full `<think>` block as-is; the other ~38% have `<think>...</think>` stripped down to just the post-think text (verified byte-for-byte against raw OT3). Median ~2450 tokens, 51.0% truncate at seqlen=2048. Incompatible with Qwen3 (wrong special tokens) — do not use for training, kept only as a reference/comparison point. |
| **PLAIN-200K** | `ot3_fineweb_200k_qwen3_train.jsonl` | Qwen3 | Built 2026-08-01/04. No truncation mitigation — median ~16.8k tokens (OT3 responses commonly run very long), 80.3% truncate at seqlen=2048, and ~26.5% of truncated rows lose the final `\boxed{}` answer entirely. This is the dataset behind the "TR-GMP got worse after 08-04" regression. |
| **THINKSTRIP-200K** | `ot3_fineweb_200k_qwen3_thinkstrip.jsonl` | Qwen3 | Built 2026-08-08 via `scripts/build_ot3_fineweb_dataset.py --strip_think_if_long`, reproducing the LEGACY-20K mechanism on purpose: if a rendered conversation exceeds seqlen(2048) tokens, drop `<think>...</think>` and keep only the post-think write-up. No length-based filtering, so domain mix (math/code/science) is untouched. Measured 48.5% truncation at seqlen=2048 (slightly better than LEGACY-20K's 51.0%). ~62% of rows have no short "clean final answer" to fall back to (the whole response is reasoning with no separate wrap-up) and stay long even after stripping — expected, not a bug. **First sweep results (2026-08-09) show math500 consistently LOWER than PLAIN-200K at matched hyperparams across s50/s60/s70** — hypothesis: removing the raw `<think>` reasoning trace (even though it fixes truncation) may cost more than it saves, since the model learns less step-by-step reasoning behavior. Not yet conclusively better than PLAIN-200K for training. |
| **RQAT-200K** | `ot3_fineweb_200k_qwen3_reasoningqat.jsonl` | Qwen3 | Built 2026-08-09 via `scripts/build_ot3_fineweb_dataset.py --min_tokens 2048 --pack_fineweb`, an exact replication of the [ReasoningQAT](https://github.com/yasu0001/ReasoningQAT) (`datautils_block.py`) data recipe: OT3 rows are kept only if they render to >= seqlen(2048) tokens (discard shorter, front-truncate the rest — every kept row is guaranteed cut before its final answer, opposite of THINKSTRIP-200K), and FineWeb-Edu docs are concatenated (bos+text+eos) into a running buffer until it reaches seqlen tokens, then cut as one packed sample (not filtered individually — median FineWeb doc is well under seqlen). 196,545 rows (160k OT3 + 36.5k packed FineWeb, slightly short of the 40k FineWeb target due to pool exhaustion). Comparison arm only, not expected to fix the truncation/final-answer problem (ReasoningQAT's own use case is QAT calibration at seqlen=8192, not final-answer accuracy at seqlen=2048). Found 90.5% row-content overlap with PLAIN-200K's OT3 portion (same seed=42, same pool) — largely redundant as a comparison arm. |
| **CALIB-POOL** (undocumented until 2026-08-09) | `ot3_fineweb_200k_qwen3.jsonl` | Qwen3 | Pre-existing 200k-row file (built 2026-08-01, 200000 rows vs PLAIN-200K's 180000) that ALPS/SparseLLM's `--data_path` scripts actually use as one-shot pruning calibration data (`ALPS/slurm_alps_prune_*.sh`, `SparseLLM/slurm_sparsellm_prune_*.sh`). Distinct file from PLAIN-200K, not previously named/tracked. Domain/leakage stats are in the same ballpark as PLAIN-200K (see leakage table below) so treat it as effectively the same generation as PLAIN-200K, just an earlier/differently-filtered cut. |
| **100%-OT3** | `ot3_100pct_qwen3.jsonl` (+ `_100k.jsonl` truncated copy) | Qwen3 | Built 2026-08-09 via `--ot_ratio 1.0`, replicating [ReasoningQAT](https://github.com/yasu0001/ReasoningQAT) Stage 2 (`main_e2e_distill.py`): 100% OpenThoughts3, zero FineWeb-Edu, seqlen=8192, plain truncation (no special filtering). Used for the seqlen=8192 NTP+KD+OPD sweep (12 jobs, `--gmp_gradient_checkpointing=true` needed to fit A100-80GB at step-32 mask-update memory spike). |

**MATH-500 verbatim-leakage check (2026-08-09, chunk-substring matching against `HuggingFaceH4/MATH-500`, methodology also applied to GPQA-diamond/IFEval/GSM8K which all came back 0% everywhere):**

| Dataset | MATH-500 leakage |
|---|---|
| Raw OpenThoughts3-1.2M (100k-sample baseline) | 0.007% |
| LEGACY-20K | 0.135% |
| THINKSTRIP-200K | 0.192% |
| PLAIN-200K / CALIB-POOL / RQAT-200K / 100%-OT3 | 0.267–0.271% (all statistically the same) |

LEGACY-20K is the *least* contaminated of everything built here — so its training advantage over THINKSTRIP-200K/PLAIN-200K is NOT explained by leakage. Domain mix (math/code/science ~71/21/8% in all three) and code-difficulty distribution (mean ~7.96/median 8 in all three) were also checked and are statistically identical across LEGACY-20K/PLAIN-200K/THINKSTRIP-200K — also ruled out. The DeepSeek-vs-Qwen3 chat-template-token difference (LEGACY-20K uses `<｜User｜>`/`<｜Assistant｜>`, shredded into ~2x garbage subwords by Qwen3's tokenizer) does not break the `<think>`-substring-based loss masking in `gkd_admm_trainer.py`'s `MixedTextDataset`, so it doesn't explain the gap either.

**ROOT CAUSE FOUND (2026-08-09): THINKSTRIP-200K's `--strip_think_if_long` silently fails for 61% of rows.** Random 2000-row sample: THINKSTRIP-200K has a "double-think" artifact (`<think>\s*</think>\s*<think>` — an empty think block immediately followed by a second, unclosed one) in 61.0% of rows, and of those, **100% are still over the 2048-token seqlen limit** (i.e. the strip did nothing for them). The remaining 39% (no artifact) are cleanly stripped, with only 2.4% still over 2048. LEGACY-20K has **0%** double-think artifact rows in the same-size sample — its strip mechanism (whatever the lost build script did) works uniformly.

Mechanism: when `_render_ot(..., strip_think=True)` cuts off the raw `<think>...</think>` block and re-renders through Qwen3's `apply_chat_template`, the template auto-inserts an empty `<think>\n\n</think>\n\n` stub in front of any assistant content that doesn't itself start with `<think>`. If the *original* raw OT3 content already contained a stray/incomplete second `<think>` further in (e.g. the model re-opens reasoning after seeming to conclude), the strip logic's `rfind("</think>")` matches the newly-inserted empty stub's close tag instead of the real one, so "everything after the real `</think>`" ends up being the *entire original unstripped reasoning trace* — no shortening happens at all. These un-stripped rows are exactly the "still very long / no clean wrap-up" cases spot-checked earlier and are disproportionately garbled (mid-CoT language-mixing artifacts, no final `\boxed{}`, cut off mid-sentence at the 2048 boundary during training).

Net effect: despite near-identical aggregate stripped/full-think percentages between LEGACY-20K and THINKSTRIP-200K, THINKSTRIP-200K's "stripped" bucket is mostly fake — 61% of its rows get zero benefit and train on truncated garbage, while LEGACY-20K's strip mechanism actually works on ~100% of rows. This is the leading explanation for LEGACY-20K's large, consistent math500 advantage. **Fix applied (2026-08-10)**: `_render_ot()` now assembles the ChatML wrapper manually (`_manual_render()`) instead of calling `tok.apply_chat_template()`, which was unconditionally collapsing any assistant content containing `</think>` down to a fresh empty stub + text-after-last-`</think>` regardless of what our strip logic had already done. Verified on a 20k rebuild: double-think artifact rate dropped from 61-63% to **0%**, matching LEGACY-20K. 50k version built as `ot3_fineweb_50k_qwen3_thinkstrip_fixed.jsonl` (job 707153, cached via job 707154) for the next TR-GMP sweep (jobs 707163-707174, s50/s60/s70 x kl{0.01,0.02} x lr{5e-5,1e-4}, mask_interval=32, seqlen=2048).

**However, a seqlen=8192 sweep (jobs 706571/706657-706667, 100%-OT3 dataset — which still HAS the double-think bug, unfixed, 61.7% artifact rate) beat every LEGACY-20K number anyway**, just by removing truncation pressure (seqlen 2048→8192, near-zero math500 truncation rate):

| Sparsity | Best seqlen=8192+100%-OT3 (buggy data) | LEGACY-20K best (seqlen=2048) |
|---|---|---|
| S50 | **73.0** (lr5e-5, mi16) | 69.0 |
| S60 | **65.6** (lr1e-4, mi16) | 53.6 |
| S70 | **43.0** (lr1e-4, mi16) | ~0 (collapse) |

This means increasing seqlen (removing truncation entirely) may matter more than fixing the double-think rendering bug — the two are somewhat confounded (the bug only matters when its 100%-still-truncated rows actually get cut, which barely happens at seqlen=8192). The 50k-fixed-data sweep at seqlen=2048 (707163-707174) is the controlled comparison that will show whether the render fix has value independent of seqlen.
