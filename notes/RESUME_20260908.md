## DO NOT simply retry: both frozen-pool arms fail reproducibly

s70_B1frozen_delta0.02 (died step 39, 10:56) and s70_A3B1jump_delta0.02 (died
step 43, 11:21) failed identically:

    [rank1] ProcessGroupNCCL's watchdog got stuck for 480 seconds
            without making progress in monitoring
    [rank1] Terminating the process after attempting to dump debug info
    exitcode -6 (SIGABRT), no error on rank 0

The one variable that separates them from the arm that DID finish:

    s70_A3jump      ro=32     initial pool    256   -> completed, avg5 42.864
    s70_B1frozen    ro=4096   initial pool  16384   -> died step 39
    s70_A3B1jump    ro=4096   initial pool  16384   -> died step 43

Only the frozen-pool path breaks, and it did NOT break before: the original 8B
B1 run built a pool of 8192 and finished. The OPKD sharding fix multiplies the
pool by world_size, so the frozen pool went 8192 -> 16384 and that is where it
falls over. The original driver script already flagged this exact spot as the
risk -- the frozen pool is generated on rank 0 and shipped in ONE
broadcast_object_list, which it called "the one step with no 4B precedent".
Rank 1 sits in that collective and its watchdog gives up after 480s.

Neither run reached step 256, so both checkpoint dirs are empty; there is
nothing to resume from and a naive relaunch will simply die again.

Options for whoever picks this up, roughly in order of effort:
  1. Raise the watchdog budget for these two arms only:
     TORCH_NCCL_HEARTBEAT_TIMEOUT_SEC (monitor thread) and/or set
     TORCH_NCCL_ENABLE_MONITORING=0 to disable the stuck-watchdog killer. The
     process-group timeout itself is already 2h (elsa/main.py:240), so the
     collective would be allowed to finish.
  2. Chunk the pool broadcast in _opkd_broadcast_pool instead of one
     broadcast_object_list of 16384 rollouts.
  3. Run these two arms at world_size=1 (single GPU) where no broadcast happens
     at all -- but 8B PGD does NOT fit on one GPU (measured: OOM at step 8,
     "Tried to allocate 4.64 GiB, 2.59 GiB free"; FSDP sharding of the optimizer
     state is what makes it fit), so this only works at 4B.

The 4B A3B1jump arm queued in logs/ablation4b_jump/ uses ro=4096 as well and is
single-GPU, so it does not take the broadcast path -- it should be unaffected.
