## Gotchas found the hard way today

1. **Never edit a running bash script in place.** bash reads a script by byte
   offset as it executes. Editing `eval_8b_long.sh` on 2026-09-20 shifted
   every later offset under two running jobs; both resumed mid-word inside
   `--skip_zeroshot`, printed `line 123: o-shot: command not found`, and re-ran
   their whole benchmark suite — 5.6 GPU-hours and two duplicate wandb runs.
   Write a new file and `mv` it over: rename keeps the running process on the
   old inode.
2. **`eval_full.py` exits 0 even when every benchmark died.** An
   `EngineDeadError` run and an OOM run both reported rc=0 with no metrics.
   `run_4b_curve.sh` now counts `results_*.json` and logs `INCOMPLETE` when
   fewer than 5 landed. Check for that string before trusting a DONE.
3. **Free-GPU detection must look at processes, not memory.** eval_full.py
   drops its vLLM engine between benchmarks, so a busy card reads near-empty
   for minutes. A memory-only check started a second job on gpu0 on 09-20 and
   cost `alps_s70` seed0 its LCB and GSM8K to OOM. `gpu_busy()` in
   `seed_worker.sh` / `run_4b_curve.sh` now also matches any `eval_full.py` /
   `resume_eval_lighteval.py` whose `CUDA_VISIBLE_DEVICES` is that card.
4. **`pop()` left the last queue line in place.** `grep -v ... && mv` skips the
   mv when grep filters out the only line, so the final task ran twice. Fixed
   to an unconditional mv.
5. **The 4B launchers defaulted to the 8B wandb project** (fork inheritance).
   Both 4B PGD trainings logged into `reasoning_qwen3_8b_nostrip8192`. Harmless
   this time — harvest admits a run only if it has `<bench>_avg_gen_cap`, and
   their evals were killed — but fixed in commit `b9cfaee`. Pass
   `--wandb_project reasoning_qwen3_4b_nostrip8192` explicitly when evaluating.
6. **`flock` does not work on this Lustre mount.** Two workers started at the
   same instant popped the same task. Start queue workers staggered, and
   confirm the queue shrank before starting the second.

## Before starting ANY eval: check wandb for a duplicate

`b200_scripts/wandb_dup_check.py <project> <run_name> <seed> [model_path]`
exits 0 if that eval is already covered, 1 if not, 2 if wandb was
unreachable. Covered means the same TSV cell (harvest's own label + sparsity
+ seed, parsed out of harvest_long_tsv.py so the two cannot drift) or the same
checkpoint (exact `config.model_path` match over its local/Hub spellings),
and either finished at 5/5 long-profile benchmarks or running with a
heartbeat under 30 min. A run that lost benchmarks to OOM does NOT count.

Wired in already: `eval_8b_long.sh` drops covered seeds and exits 0 if none
remain; `eval_long_dedup.sh` is the same guard around a bare eval_full.py
call. Verified on known cases (2-22 s each): 4B s70 alpsretrain 3term s42 ->
dup (n84 running), 2term s1 -> dup (n86), alpspgdnotr s42 -> none, 8B s80
alps s1 -> dup (bdqripdh finished 5/5), and a deliberately misnamed run on the
2term checkpoint -> dup via model_path.

Why: on 2026-09-21 this box spent 4.8 GPU-hours on a 4B eval that n84 was
already running, and none of the three machines can see each other's queues.
Known gap: an old-style Hub id (gmp-kd3e-1-...) does not map back to a local
dir name, so path matching misses it -- the label match still catches it if
the run is named s3_<size>_<arm>_s<NN>_seed<N>.

## Naming so results land in the right TSV block

`harvest_long_tsv.py` derives a block label from the run name: it strips
`s3_<size>b_`, `_seedN`, and the `_sNN` sparsity token, then looks the rest up
in `METHOD`. Labels already registered for these arms (commit `74a09a2`):
`alpspgdtr` → "ALPS + PGD (trust region)", `alpspgdnotr` → "ALPS + PGD (no
trust region)". So name eval runs `s3_4b_alpspgdtr_s70_seed42` and they merge
correctly. Get this wrong and the arm opens a second one-seed block.
